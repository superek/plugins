# loop:retro — 사고 1건 = 자산 1개

## Quality Gate (통과 못 하면 아무것도 저장하지 않고 그렇게 말한다)

1. **놀랐는가** — 예상과 실제가 어긋난 지점이 있어야 한다. 없으면 그냥 작업이지 교훈이 아니다.
2. **재발 가능한가** — 이 프로젝트에서만, 이번 한 번만 생길 일이면 저장하지 않는다.
3. **한 문장 규칙으로 줄여지는가** — 못 줄이면 아직 원인을 모르는 것이다. Step 2로 돌아간다.

---

## Step 1 — 사건 3줄

```
증상:  <겉으로 보인 것>
기대:  <내가 예상했던 것>
실제:  <실제로 일어난 것>
```

기대와 실제의 **차이**가 이 회고의 전부다. 여기가 비면 나머지는 의미 없다.

## Step 2 — 근본 원인 (5 Why 대신 1개만)

- "왜?"를 **차이가 사라질 때까지** 내려간다. 보통 2~3번이면 닿는다.
- 멈추는 기준: **"이걸 알았으면 안 틀렸다"** 는 지점.
- ⚠️ "실수했다", "확인을 안 했다"는 원인이 아니다. **그 실수가 가능했던 구조**가 원인이다.

```
표면: 목록이 새로고침 안 됨
  왜? 캐시가 그대로라서
  왜? 저장 후 무효화를 안 걸어서
  왜? 이 API가 목록 캐시에도 영향을 준다는 걸 몰라서   ← 여기가 원인
```

## Step 3 — 재발 신호 (Recognition Signal)

**"다음에 무엇을 보면 이 교훈을 떠올려야 하는가"** 를 한 문장으로.

- ❌ "캐시를 조심하자" (신호가 아님 — 언제 떠올릴지 모름)
- ✅ "쓰기(mutation) API를 추가할 때, 그 데이터를 읽는 화면이 하나라도 있으면"

이 문장이 나중에 스킬 `description`의 트리거가 된다.

## Step 4 — 규칙 1개

재발 신호 + 그때 할 행동을 한 줄로 합친다. **여러 개 쓰지 않는다.** 하나만.

```
쓰기 API를 추가하면, 같은 데이터를 읽는 쿼리 키를 찾아 무효화를 같이 넣는다.
근거: <티켓키 또는 PR 링크>
```

근거(티켓·PR·커밋)를 반드시 붙인다. 이게 6개월 뒤 "왜 이 규칙이 있지?" 의 답이 된다.

## Step 5 — 저장 위치 판정

| 성격 | 저장처 |
|---|---|
| 이 레포에서만 통하는 규약 | `<repo>/.claude/skills/<주제>.md` — 기존 파일이 있으면 **거기에 추가** |
| 언어/프레임워크 일반 지식 | 전역 스킬 → `loop:skill-standard` 로 넘긴다 |
| 나에 대한 사실·선호 | 메모리 (`memory/`) |
| 프로젝트 상태·진행 상황 | 프로젝트 메모/계획 문서 |
| 위 어디에도 안 맞음 | **저장 안 함.** 그렇게 말하고 끝낸다 |

### 새 파일보다 기존 파일 흡수가 먼저

같은 주제가 이미 있으면 **새 파일을 만들지 않고** 원본 끝에 한 줄로 누적한다.

```markdown
## 후속 보정 메모

- YYYY-MM-DD: <변경 요약 한 줄> (사유: <왜>)
```

- **흡수 대상**: 기존 교훈의 정정·보강, 같은 원인의 재발 사례
- **신규 대상**: 주제가 다른 새 교훈, 원본을 통째로 대체할 만한 재설계

> 실제 사례: 작은 보정마다 파일을 하나씩 늘렸더니 목록이 노이즈로 찼고, "사례 N건"이라는 숫자의 의미가 흐려졌다. N건은 **독립적인 사이클** N개여야 값이 있다.

### 낡을 수 있는 사실은 유효기간을 같이 적는다

"현재 이렇다"는 기록은 **반드시 낡는다.** 저장할 때 재확인 방법을 한 줄 붙인다.

```markdown
확인일: 2026-08-26 · 재확인: `<명령어 또는 파일 경로>` 로 지금도 그런지 본다
```

> 근거: 한 메모리가 스스로 *"이 메모리 자체가 「기록이 낡는다」의 실증 사례"* 라고 적혀 있다 — 이미 고쳐진 실패를 "실패 중"으로 몇 달간 붙들고 있었다. 낡는 건 막을 수 없으니 **낡았는지 확인하는 법**을 남긴다.

원리(왜 그런가)는 안 낡고, 상태(지금 어떤가)는 낡는다. **원리 위주로 쓰면 유효기간이 필요 없다.**

### 좁은 곳 → 넓은 곳으로 올릴 땐 고유값을 벗긴다

프로젝트 메모리·로컬 스킬을 **전역 스킬로 승격할 때**, 경로·브랜치명·포트·호스트·도구명은 그 프로젝트의 **사실**이지 원리가 아니다. 본문에 그대로 박으면 다른 프로젝트에서 **규칙으로 읽힌다.**

셋 중 하나로 처리한다:
1. **예시 칸으로 내린다** — 표의 "예시(프로젝트마다 다름)" 열로
2. **판정 절차로 바꾼다** — "X를 써라" → "X를 찾는 방법 + 못 찾으면 묻는다"
3. **못 벗기겠으면 승격하지 않는다** — 로컬에 그대로 둔다

**검산 한 문장:** *"다른 프로젝트에서 이 문장을 그대로 실행하면 어떻게 되나?"*
- **에러가 난다** → 시끄러운 실패. 시간만 날리고 드러난다
- **성공하는데 답이 틀린다** → **조용한 실패. 이게 위험하다** — 우선 순위를 여기에 둔다

> 근거: 2026-08-26. `/v3/api-docs` 를 본문에 박았다(Spring+springdoc 전용 — 다른 스택이면 404, 시끄러운 실패). 같은 원인으로 `git diff main...HEAD` 도 박혀 있었다 — 이건 **base가 틀려도 명령이 성공해서** 엉뚱한 범위를 리뷰하게 된다. 원인은 하나였다: 메모리를 옮기며 "그 프로젝트의 사실"과 "일반 원리"를 안 갈랐다.

## Step 6 — 이해도 확인 1문항

저장 후, 이 교훈으로 **내가 답해야 하는 질문 1개**를 낸다. 정답은 먼저 쓰지 않는다.

예: "이번과 같은 구조인데 캐시가 아니라 로컬 상태였다면, 같은 증상이 나왔을까요?"

## 금지

- ❌ 원인을 "실수" / "확인 부족" 으로 적기
- ❌ 규칙을 3개 이상 뽑기 (하나도 기억 못 하게 된다)
- ❌ 재발 신호 없이 규칙만 저장 (= 다시는 안 읽히는 문서)
- ❌ 근거 링크 없이 저장
- ❌ 기존 스킬 확인 없이 새 파일 만들기
- ❌ 회고할 게 없는데 억지로 만들어내기 — "이번엔 교훈 없음"이 정상적인 결론이다
