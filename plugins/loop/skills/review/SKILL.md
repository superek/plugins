# loop:review — 내 검증 루틴

## Quality Gate (이 6개를 못 지키면 리뷰 결과를 내지 않는다)

1. **스펙 없이 리뷰하지 않는다.** 무엇이 "맞는 동작"인지 근거를 먼저 확보한다.
2. **모든 지적에는 실패 시나리오가 붙는다.** "입력 X + 상태 Y → 잘못된 결과 Z". 못 쓰면 버린다.
3. **코드 사실과 화면 사실을 섞지 않는다** (Phase 3).
4. **적대적 재검증을 통과한 것만 보고한다** (Phase 3).
5. **마지막에 이해도 퀴즈를 낸다** (Phase 5). 생략 대상이 아니다.
6. **이번에 직접 돌리지 않은 검증을 "통과"라고 쓰지 않는다.** 주장마다 필요한 증거는 `checks.md` §9.

---

## Phase 0 — 기준(base) 확정 → 규모 판정 (결정적)

**base를 추측하지 않는다.** base가 틀려도 `git diff` 는 멀쩡히 성공하기 때문에 **조용히 엉뚱한 범위를 리뷰하게 된다.** (404처럼 소리가 나지 않는다)

```bash
git fetch origin --quiet
git branch -r --list 'origin/release/*' 'origin/main' 'origin/develop'   # 후보 확인
git diff --stat origin/<base>...HEAD                                     # 확정 후 실행
```

- **base에는 항상 `origin/` 을 붙인다.** 로컬 브랜치는 상시 뒤처져 있어서, 로컬 기준으로 재면 남의 변경이 내 diff에 섞인다.
- **기본 브랜치가 `main` 이라고 가정하지 않는다.** PR 머지 타겟이 `release/<버전>` 인 팀이면 그쪽이 base다.
- 후보가 여럿이거나 못 찾으면 → **묻는다.** 확정 전에는 Phase 1로 넘어가지 않는다.
- 확정한 base를 **판정 한 줄에 같이 적는다.** 예: `base=origin/release/1.4 · 규모 M`

| 규모 | 기준 | 렌즈 | 서브에이전트 |
|---|---|---|---|
| **S** | 파일 ≤ 3, 순수 UI/문구/설정 | 1·2 | 0개 (직접) |
| **M** | 파일 4~15, 로직 변경 포함 | 1~4 | 2~3개 |
| **L** | 파일 16+, 마이그레이션·인증/권한·외부 연동 | 1~5 | 4~5개 |

판정을 **한 줄로 먼저 말하고** 진행한다. 예: `base=origin/release/1.4 · 규모 M — 렌즈 1~4, 에이전트 3개`

## Phase 0.5 — 기계적 검사 (판단 0, 30초)

**렌즈로 훑기 전에 명령어로 걷어낸다.** 지적의 상당수가 여기서 나온다 — 디버그 잔여물, **비활성화된 테스트**(CI는 초록인데 커버리지가 빈다), 새 TODO, 시크릿, 커밋되면 안 되는 파일, 빌드·타입·린트, 최신 base 재검증.

→ **명령어 전체는 `checks.md`.** Phase 0 에서 확정한 `$BASE` 를 넣고 돌린다.

결과를 한 줄로 보고한다. 예: `기계검사: 잔여물 0 · 비활성테스트 1건 · 시크릿 0 · 빌드 통과`

## Phase 1 — 스펙 확보 (블로킹)

- 티켓이 있으면 **Acceptance Criteria** 부터 읽는다.
- 프로젝트 로컬 스킬(`.claude/skills/`)의 규약을 체크리스트로 변환한다.
- **grep 히트 줄만 보고 판단하지 않는다.** 그 줄이 속한 블록(함수·섹션·표)을 통째로 읽는다. (실제 사례: 같은 원인으로 **네 번** 오판. 시안이 이미 바뀐 단위를 쓰고 있었는데 검색에 걸린 줄만 보고 "단위를 바꿔야 한다"고 보고 → 값 변환 로직을 건드려 회귀를 낼 뻔했다)
- 스펙을 못 찾으면 1회 묻는다. 답이 없으면 "스펙 미확인"을 리포트 맨 위에 박고 진행한다.

## Phase 2 — 다축 렌즈 검사

| # | 렌즈 | 보는 것 |
|---|---|---|
| 1 | **스펙 정합** | AC를 만족하나. 빠진 요구사항, 몰래 늘어난 범위 |
| 2 | **정확성·엣지케이스** | null/빈배열/0/음수/경계값, 첫 렌더, 동시 클릭, 실패 응답. **실데이터에 없는 값은 만들어서 본다** |
| 3 | **데이터·상태** | 상태 소유자, 캐시 무효화, 트랜잭션 경계, N+1. **판정(boolean)이 화면에 있으면 모델로 올라가야 하는 신호** |
| 4 | **보안·권한** | 인가를 서버에서 강제하나, 입력 검증, 로그의 민감정보 |
| 5 | **유지보수** | 6개월 뒤 읽고 고칠 수 있나. 중복, 이름, 죽은 코드 |

**렌즈별 독립 실행.** 서로의 결과를 보지 않게 한다. 발견은 `{파일:줄, 한줄요약, 실패시나리오, 심각도}` 로만.

### 렌즈 2·3에서 반드시 걸어야 할 3가지

- **props/인자 체인은 호출부부터 끝까지 추적한다.** 내부 가드가 아무리 있어도 들어오는 props가 매 렌더 새 참조면 무의미하다. (실제 사례: 훅 내부만 분석하고 무한 루프를 "위험 없음"으로 오판했다)
- **정적 검증 통과는 검증이 아니다.** 타입체크·린트·테스트가 전부 PASS인데 결함 5건이 나온 적이 있다 — 원인은 "모국어 로케일 + 실데이터만 봤다". 다국어 라벨은 고정폭에서 깨지고, 0/null/100% 초과 같은 경계값은 실데이터에 없다.
- **공용 컴포넌트/공용 값을 내 화면에 맞추려고 바꾸지 않는다.** 옵셔널 prop + 기존값 폴백으로.

## Phase 3 — 적대적 재검증 (필수)

Phase 2 발견을 그대로 믿지 않는다. **아래 3개 도구로 반박을 시도한다.**

### ① 코드 사실 / 화면 사실 가르기
- **코드 사실** = "이 줄이 이렇게 쓰여 있다" — 읽으면 확정
- **화면 사실** = "그래서 사용자에게 이렇게 보인다" — **그 코드에 도달하는 데이터가 실재해야** 확정

코드 사실로 화면 사실을 단정하지 않는다. 도달조차 못 하면 원인이 딴 데 있다.
> 실제 사례: 코드상 "이 분기가 값을 0으로 접는다"는 참이었다. 그런데 서버가 이미 반올림된 값을 보내고 있어서 **그 분기는 실행조차 되지 않았다.** 그대로 보고했으면 없는 버그를 고치러 갔을 것이다.

### ② 대조군 만들기 — 구분력 없는 관측은 증거가 아니다
"이 관측이 **반대 가설에서도 같은 값**을 내나?" 같으면 아무것도 증명 못 한 것이다. 실행을 반복해도 안 갈리면 **명세를 연다.** (실제 사례: 올바른 enum 값도 0건, 존재하지 않는 값도 0건이라 「정말 없음」과 「서버가 못 알아들음」이 겉으로 똑같았다)

### ③ 과교정 금지 — 정정을 받으면 내 데이터에 대입한다
"같은 유형이니까"로 수용하지 않는다. **내 숫자에 넣어 결론이 바뀌는지** 본다. **과교정은 원래 결함만큼 비싸다.** (실제 사례: 두 가설이 같은 값을 내던 건 내 쪽 대상 건수가 0이라서였고, 건수가 있는 쪽에서는 값이 갈렸다. 유효한 근거를 잘못 철회했다)

반박이 성립하면 버린다. 애매하면 `추정` 딱지를 붙여 남긴다.

## Phase 3.5 — 묶임 묻기 (관측이 끝난 뒤에만)

**개별 결함을 다 모은 뒤** 한 번에 훑어서 "이것들이 한 원인인가"를 묻는다.
- 관측 **중에** 묶으려 하면 덜 모인 상태라 틀린다.
- 묶었다고 개별 항목을 지우지 않는다 — **근거는 개별 항목이 갖고 있다.** "같은 원인" 표시만 단다.
> 실제 사례: 표시 형식 결함 3건을 각각 독립 결함으로 적었는데, 다섯 번째 라운드에서 원인이 **하나**로 판명됐다 — 한 화면만 공용 컴포넌트를 쓰지 않고 자기 렌더링을 만든 것이었다. 조치가 "세 곳 고쳐라"에서 "하나 고쳐라"로 바뀌었다.

## Phase 4 — 리포트

심각도 순, **최대 7건.** 넘치면 "N건 더 있음"을 명시한다(조용히 자르지 않는다).

```
[치명] 파일:줄 — 한 줄 요약
  실패: <입력/상태> → <잘못된 결과>
  근거: <AC 항목 or 규약 문서 §>   구분: 코드사실 / 화면사실 / 추정
  수정안: <1~2줄>
```

심각도: `치명`(데이터 손상·보안·장애) > `높음`(스펙 위반·명백한 버그) > `보통`(엣지케이스) > `낮음`(유지보수)

**심각도와 수정 주체(자동/사람)는 직교하는 두 축이다** — 치명인데 자동으로 고칠 수 있는 것도, 사소한데 사람이 정해야 하는 것도 있다. 판정표와 수정 절차는 → `checks.md` 「수정 요청을 받았을 때」.

**화면이 바뀌는 변경이 있으면** 리포트 끝에 확인 절차를 붙인다 — "무엇을 눌러서 무엇이 보여야 하는지". 정적 검증 통과만으로 "이상 없음"이라 쓰지 않는다.

## Phase 5 — 이해도 퀴즈 (생략 금지)

내가 직접 답해야 하는 질문 **2~3개**. 이번 diff에서 나온 것만 소재로.
- **한 문장, 일상 단어, 구체적.** 조건절을 여러 개로 꼬지 않는다.
- **정답을 먼저 쓰지 않는다.** 내가 답한 뒤에 피드백한다.

## 비용 통제

규모 S는 서브에이전트 0개(판정 없이 팬아웃 금지). diff와 그 주변만 읽고, 파일 전체는 렌즈 3·4에서 필요할 때만.

## 금지

- ❌ 스펙 없이 "좋아 보인다" / "LGTM"
- ❌ 실패 시나리오 없는 지적 (= 취향)
- ❌ grep 히트 줄만 보고 구조 단정
- ❌ 코드 사실을 화면 사실로 승격
- ❌ 반대 가설에서도 같은 값이 나오는 관측을 근거로 쓰기
- ❌ 적대적 재검증 건너뛰기
- ❌ 관측 중에 결함 묶기 / 묶으면서 개별 근거 지우기
- ❌ 발견 건수를 조용히 줄여 "다 봤다"처럼 보이게 하기
- ❌ 이번에 안 돌린 검증을 "통과"라고 쓰기 / 정적 검사 초록불을 안전 신호로 읽기
- ❌ 퀴즈에 정답 같이 적기
- ❌ 리뷰 중 코드 수정 (리뷰는 읽기만)
