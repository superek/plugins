# loop:review — 기계적 검사 · 수정 안전 루프

SKILL.md 의 **Phase 0.5** 와 **수정 요청을 받았을 때** 참조한다.

판단이 필요 없는 것부터 걷어내면, 렌즈 검사(Phase 2)를 설계와 로직에 쓸 수 있다.
리뷰에서 나오는 지적의 상당수는 **명령어 몇 줄로 30초에 잡힌다.**

---

## 준비 — base와 대상 파일 고정

**`main` 을 가정하지 않는다.** Phase 0 에서 확정한 base를 변수에 넣고 시작한다.

```bash
BASE=origin/release/1.4             # ← Phase 0 결과를 넣는다
FILES=$(git diff $BASE --name-only --diff-filter=ACM)
git diff --stat $BASE...HEAD
```

## 1. 디버그 잔여물

```bash
grep -rnE "console\.(log|debug)|debugger;|println\(|System\.out\.print|printStackTrace\(\)" $FILES
```

## 2. 비활성화된 테스트 (⚠️ 가장 조용한 결함)

**CI를 초록색으로 만든 채 커버리지를 비운다.** 통과 배지만 보면 절대 안 보인다.

```bash
grep -rnE "\.only\(|\.skip\(|xit\(|xdescribe\(|@Disabled|@Ignore" $FILES
```

## 3. 새로 들어간 TODO

기존 TODO 말고 **이번 diff에서 추가된 것만** 본다.

```bash
git diff $BASE | grep "^+" | grep -nE "TODO|FIXME|XXX|HACK"
```

## 4. 자격증명·비밀값

```bash
git diff $BASE | grep "^+" | grep -niE "(api[_-]?key|password|secret|token)[[:space:]]*[:=][[:space:]]*['\"][^'\"]{8,}"
git ls-files | grep -E "\.env$|\.pem$|credentials|id_rsa"
```

## 5. 커밋되면 안 되는 것

```bash
git status --porcelain
git ls-files | grep -E "\.idea|\.vscode/|\.DS_Store|node_modules|/build/|/target/|\.class$"
```

## 6. 빌드·타입·린트·테스트

**명령어를 추측하지 않는다.** 저장소에서 먼저 찾는다.

```bash
cat package.json 2>/dev/null | grep -A20 '"scripts"'   # JS/TS
ls gradlew pom.xml 2>/dev/null                          # JVM
```

찾은 것으로 돌린다. JVM은 **`clean` 을 붙여야 캐시 착시를 피한다.**
Turbo·Nx 같은 캐시 러너는 변경 파일이 있는데 cache hit이면 **패키지 안에서 직접 한 번 더** 돌린다.

## 7. 최신 base에서 재검증

내 브랜치에서만 통과하는 변경은 머지 후에 base를 깨뜨린다.

```bash
git fetch origin --quiet
git log --oneline HEAD..$BASE          # base가 앞서 나갔나?
```

**앞서 나갔으면** — 어느 쪽으로 맞출지는 push 여부로 갈린다:

| 상태 | 방법 | 이유 |
|---|---|---|
| 아직 push 안 함 | `git rebase $BASE` | 히스토리가 깨끗 |
| **이미 push 함** | `git merge $BASE` | rebase 하면 **force push가 필요**해진다 |

⚠️ **이미 push한 브랜치를 rebase 하지 않는다.** 리뷰어가 보던 커밋이 사라지고, 남이 그 브랜치를 받아갔으면 충돌이 난다.

맞춘 뒤 6번을 다시 돌린다. 여기서 깨지면 **남의 변경과의 충돌**이고, 지금 아는 게 머지 후보다 훨씬 싸다.

## 8. 공개 레포에 처음 push 하기 전 (되돌리기가 가장 비싼 검사)

**push는 사실상 되돌릴 수 없다.** force push를 해도 호스팅 서비스는 옛 커밋을 SHA로 한동안 계속 제공한다. 완전히 없애려면 레포를 지우거나 지원팀에 요청해야 한다. **밀기 전이 유일하게 싼 시점이다.**

⚠️ **시크릿 스캐너(gitleaks 등) 통과는 이 검사를 대체하지 않는다.** 그것들은 API 키·토큰·비밀번호 **패턴**을 찾는다. 사내 제품명·이슈 키·내부 문서 경로·인프라 구성 서술은 애초에 찾는 대상이 아니라서 **언제나 통과한다.** 초록불을 안전 신호로 읽으면 안 된다.

```bash
# 고유값 부분은 자기 조직 것으로 바꿔서 쓴다
grep -rnEi '회사명|제품코드명1|제품코드명2' .          # 제품·프로젝트 코드명
grep -rnE  '\b[A-Z][A-Z0-9]{1,9}-[0-9]+\b' .           # 이슈 트래커 키
grep -rnE  '`[a-z0-9]+(_[a-z0-9]+){2,}`' .             # 로컬 메모·메모리 파일명
grep -rnEi '내부문서폴더명|사내위키경로' .              # 내부 문서 경로
grep -rnE  'release/v?[0-9]+\.[0-9]+\.[0-9]+' .        # 실제 릴리즈 버전
grep -rnEi 'SSH 터널|공유 (dev|개발) DB|사내망|VPN' .   # 인프라 구성 서술
```

히트가 나오면 **지우지 말고 익명화한다.** 근거를 통째로 버리면 규칙이 6개월 뒤에 안 지켜진다.

| 바꾸는 것 | 남기는 것 |
|---|---|
| 파일 경로·이슈 키 | **무슨 일이 있었는지** |
| 제품·프로젝트 이름 | 어떤 구조라서 그렇게 됐는지 |
| 실제 버전·호스트·포트 | 중립 예시 (`origin/release/1.4`) |

```markdown
❌ 근거: `<로컬 메모 파일명>` — 화면에 +0%가 뜬다
✅ 실제 사례: 코드상 "이 분기가 값을 0으로 접는다"는 참이었지만, 서버가 이미 반올림된 값을
   보내고 있어 그 분기는 실행조차 되지 않았다.
```

⚠️ **이미 push한 뒤에 발견했다면 수정 커밋으로는 안 지워진다.** 히스토리에 남는다. 갓 만든 레포라면 **삭제 후 재생성**이 가장 확실하고, 오래된 레포라면 히스토리 재작성 + 호스팅 지원 요청이 필요하다.

## 9. 완료를 주장하기 전 — 주장↔증거 대응

**이번에 직접 돌리지 않은 검증은 "통과했다"고 쓸 수 없다.** 이전 실행 결과, 남의 보고, "고쳤으니 될 것"은 증거가 아니다.

| 주장 | 필요한 증거 | 불충분한 것 |
|---|---|---|
| 테스트 통과 | **이번에 돌린** 출력에 실패 0 | 이전 실행 결과, "그 파일은 안 건드렸으니까" |
| 빌드 성공 | 빌드 명령의 exit 0 | "린트가 통과했으니까" — 린터는 컴파일러가 아니다 |
| 버그 고쳐짐 | **원래 증상을 그대로 재현**해서 안 나오는 것 확인 | 코드를 바꿨으니 고쳐졌을 것 |
| 서브에이전트 완료 | `git diff` 로 **실제 변경을 직접 확인** | 에이전트가 "완료했다"고 보고함 |
| 화면 정상 | 그 화면을 실제로 띄워서 확인 | 타입체크·린트 통과 |
| 유출 없음 | 목적에 맞는 패턴으로 직접 스캔(§8) | 시크릿 스캐너 통과 — 찾는 대상이 다르다 |

**초록불은 "그 도구가 찾는 것이 없었다"는 뜻이지 "문제가 없다"는 뜻이 아니다.** 통과를 근거로 쓰기 전에 *그 도구가 무엇을 찾는 도구인지* 한 번 되묻는다.

## 10. "회귀 테스트를 썼다"고 말하기 전 — red-green 확인

**통과하는 테스트는 아무것도 검사하지 않는 테스트일 수도 있다.** 아래를 거치지 않았으면 회귀를 막는다는 증거가 없다.

1. 테스트를 쓴다 → 통과하는지 본다
2. **고친 코드를 버그가 있던 상태로 되돌린다** (사본에서 복원 — `git checkout` 금지, 아래 「수정 안전 루프」)
3. **테스트가 반드시 실패하는지 확인한다** ← 여기가 핵심
4. 수정을 다시 적용한다 → 통과하는지 본다

3번에서 그냥 통과하면 그 테스트는 이 버그를 못 잡는다. `loop:trace` 의 **대조군 만들기**와 같은 원리다 — 반대 조건에서도 같은 결과가 나오는 관측은 아무것도 증명하지 못한다.

## 수정 요청을 받았을 때 (사용자가 "고쳐줘" 라고 했을 때만)

리뷰는 기본이 읽기 전용이다. 수정은 **한 건씩 고치고 즉시 검증한다.**

### 먼저 수정 주체를 가른다 (심각도와 별개의 축)

| 수정 주체 | 뜻 | 예 |
|---|---|---|
| **자동** | 정답이 하나이고 **동작이 안 바뀐다** | 안 쓰는 import 제거, 오타, `setX(x+1)` → `setX(x => x+1)` |
| **사람** | 선택지가 여럿이거나 **동작이 바뀐다** | 에러 처리 전략(리다이렉트/토스트/재시도), 상태 위치, `div onClick` → `button` (기본 스타일이 달라져 레이아웃이 틀어진다) |

판정 순서: ① 확신 없으면 **사람** ② 동작이 바뀌면 **사람** ③ 자동으로 고쳤는데 검증 실패하면 **사람으로 격상**.

```bash
# 1. 고치기 전에 사본을 뜬다 — 이게 안전장치다
cp src/foo.ts /tmp/loop:review-backup-foo.ts

# 2. 수정

# 3. 즉시 검증 (그 파일만)
npx tsc --noEmit && npx eslint src/foo.ts

# 4. 실패하면 사본에서 복원하고 사람 판단으로 넘긴다
cp /tmp/loop:review-backup-foo.ts src/foo.ts
```

### 🛑 `git checkout -- <파일>` 로 되돌리지 않는다

그 파일에는 **아직 커밋되지 않은 작업이 통째로** 들어있을 수 있고, `git checkout` 은 그것까지 전부 날린다. 반드시 사본에서 복원한다.

### 루프 규칙

- **한 번에 한 건.** 여러 건 고치고 한 번에 검증하면 어느 수정이 깨뜨렸는지 모른다.
- 같은 파일을 **두 번 되돌리게 되면 멈추고** 사람에게 넘긴다.
- 수정 후에는 다시 훑는다 — 수정이 새 문제를 만들었을 수 있다. **재검토는 최대 2회.**
