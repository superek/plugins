# loop:skill-standard — 스킬 작성 표준

## Quality Gate (하나라도 못 지키면 파일을 만들지 않는다)

1. **미래의 나에게 필요한가** — 이번 한 번만 쓸 지식이면 스킬이 아니다.
2. **코드·문서에 이미 있는가** — 있으면 스킬 대신 그 문서를 가리키는 한 줄만 남긴다.
3. **재발 신호가 있는가** — "언제 이걸 떠올려야 하는지"를 한 문장으로 쓸 수 있어야 한다.
4. **금지 섹션이 있는가** — 하지 말 것을 못 쓰겠으면 아직 이해가 덜 된 것이다.

---

## Step 1 — 저장 위치 판정

| 지식의 성격 | 위치 |
|---|---|
| 프로젝트 무관, 내 작업 방식 | `~/.claude/skills/<name>/SKILL.md` |
| 이 레포에서만 통하는 규약 | `<repo>/.claude/skills/<name>.md` 또는 `<name>/SKILL.md` |
| 한 번 쓰고 버릴 메모 | 스킬 아님 → 그냥 답변으로 |
| "나(사용자)는 이런 사람이다" 같은 사실 | 스킬 아님 → 메모리(`memory/`) |

> 헷갈리면 **좁은 쪽(프로젝트 로컬)**에 둔다. 전역으로 올리는 건 두 번째 프로젝트에서 똑같이 필요해졌을 때.

## Step 2 — frontmatter (MUST)

```yaml
---
name: <kebab-case, 폴더명과 동일>
description: <무엇을 하는지 1문장> + <언제 부르는지 실제 말투 트리거 3~5개> + <언제 안 부르는지 1개>
---
```

- `description`은 **호출 여부를 판단하는 유일한 근거**다. 내용 요약이 아니라 **트리거 목록**으로 쓴다.
- 내가 실제로 쓰는 한국어 말투를 그대로 넣는다. ("이거 괜찮아?", "정리해줘")
- **안 불러야 할 경우도 한 줄** 넣는다. 오발동이 미발동보다 비싸다.

## Step 3 — 본문 구조

### 필수 섹션
| 섹션 | 역할 |
|---|---|
| **Quality Gate** | 절차 앞에 둔다. 통과 못 하면 진행 안 하는 조건 |
| **Step / Phase 번호제** | 각 단계마다 "산출물"을 명시 |
| **금지 (안티패턴)** | 마지막. 하지 말 것 |

### 선택 섹션
- **판단표** — 갈림길이 있으면 표 1개로. 산문으로 설명하지 않는다.
- **MUST / SHOULD 분리** — 강제와 권장을 절 단위로 나눈다. 섞으면 둘 다 안 지켜진다.
- **비용 통제** — 서브에이전트를 쓰는 스킬이면 필수.

### 분량
- SKILL.md는 **150줄 이하**를 목표로 한다.
- 넘치면 자르지 말고 **옆 파일로 뺀다** (점진 공개):
  ```
  some-skill/
    SKILL.md          ← 절차와 판단만
    reference.md      ← 표, 스펙, 긴 예시
    scripts/check.sh  ← 결정적으로 처리되는 부분
  ```
  SKILL.md에는 `자세한 표는 reference.md` 처럼 **언제 읽어야 하는지**를 적는다.

## Step 4 — 규칙마다 근거를 박는다

```markdown
- 권한 검사는 서버에서 강제한다. 근거: `docs/design/security.md §2`
- soft-delete 부모 + CASCADE 자식은 비대칭이 생긴다. 근거: PROJ-78 회고
```

근거 없는 규칙은 6개월 뒤에 "이거 왜 이랬지?" 가 되고, 그러면 아무도 안 지킨다.

⚠️ **공개하는 스킬이라면 파일 경로·티켓 키를 그대로 쓰지 않는다.** 읽는 사람이 그 파일에 접근할 수 없어 깨진 링크가 되고, 경로 자체가 내부 정보를 드러낸다. 대신 **무슨 일이 있었는지를 익명화해 서술한다.**

```markdown
❌ 근거: `<내 로컬 메모>/rounding-incident.md` — 화면에 +0%가 뜬다
✅ 실제 사례: 코드상 "이 분기가 값을 0으로 접는다"는 참이었지만, 서버가 이미 반올림된 값을
   보내고 있어 그 분기는 실행조차 되지 않았다.
```

**눈으로 확인했다고 끝내지 않는다.** 공개 레포에 처음 push 하기 전 기계로 한 번 돌린다 — 검사 명령은 `loop:review` 의 `checks.md` §8. push 후에는 수정 커밋으로 못 지운다.

## Step 5 — 결정적인 것과 판단이 필요한 것을 나눈다

- `git diff --stat`, 파일 존재 확인, JSON 파싱 → **스크립트/명령어로 고정**
- 코드가 맞는지, 어떤 설계가 나은지 → **판단 단계**

한 Step 안에 둘을 섞으면 매번 결과가 달라진다.

## Step 6 — 애매하면 멈추는 지점을 명시한다

스킬 안에 **분기 3종**을 심는다:

```
후보가 1개 → 묻지 않고 진행
후보가 여러 개 → 사용자에게 1회 묻는다
답을 못 얻음 → 기본값으로 조용히 떨어지지 말고 멈추고 보고한다
```

되돌리기 쉬운 일은 그냥 하고, 되돌리기 어려운 일(티켓 생성, 푸시, 삭제)은 멈춘다.

## 금지

- ❌ `description`에 트리거 문구 없이 기능 설명만 쓰기
- ❌ 한 스킬에 여러 목적 담기 (리뷰 + 배포 + 문서화 → 3개로 쪼갤 것)
- ❌ "베스트 프랙티스" 나열만 하고 절차가 없는 스킬
- ❌ 금지 섹션 없이 저장
- ❌ 프로젝트 고유 규약을 전역(`~/.claude/skills`)에 올리기
- ❌ 이미 있는 스킬과 겹치는 새 스킬 만들기 → 먼저 기존 걸 고칠 수 있는지 본다
- ❌ 300줄짜리 SKILL.md (→ 옆 파일로 분리)
