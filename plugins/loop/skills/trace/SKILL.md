# loop:trace — 증상 → 원인

## Quality Gate

1. **원인을 말하기 전에 "되는 것과 안 되는 것의 차이"를 하나는 갖고 있어야 한다.**
2. **증상을 원인으로 적지 않는다.** 에러 메시지 이름은 증상이다.
3. **관측이 두 가설을 구분하지 못하면 그 관측은 근거가 아니다** (Step 4).
4. **고치기 전에 인과를 확정한다** (Step 6).

---

## Step 1 — 증상을 관측 가능한 문장으로

```
기대: <무엇이 보여야/일어나야 하나>
실제: <무엇이 보이나>
범위: <항상? 특정 조건에서만? 언제부터?>
```

"안 돼요"는 증상이 아니다. **어디를 눌렀을 때 무엇이 보이는지**까지 내려와야 추적이 시작된다.

## Step 2 — 층 가르기 (가장 큰 절약)

셋 중 어디인지 먼저 가른다. 여기서 틀리면 나머지 전부가 헛수고다.

| 층 | 뜻 | 확인 방법 |
|---|---|---|
| **데이터** | 서버가 틀린 값 / 옛 값을 준다 | 네트워크 탭 응답 본문을 직접 본다 |
| **표시** | 값은 맞는데 UI가 잘못 그린다 | 응답은 맞는데 화면만 다르다 |
| **배선** | 값도 맞고 UI도 맞는데 안 전달되거나 재요청이 안 된다 | 재요청 자체가 안 나간다 / 옛 캐시를 읽는다 |

## Step 3 — 되는 것과의 차이가 화살표

**부분적으로 되는 것**을 찾아라. 그 차이가 범위를 한 번에 줄인다.

- "레벨은 바뀌는데 이름만 안 바뀐다" → 리렌더는 되고 있다 → **이름 계산 로직**으로 좁혀짐
- "A 화면은 되는데 B 화면은 안 된다" → 같은 데이터, 다른 렌더 경로 → **B의 렌더 경로**
- "어제는 됐다" → `git log` / 배포 시각과 대조

되는 케이스가 하나도 없으면 **일부러 만든다** (다른 계정, 다른 값, 다른 로케일).

## Step 4 — 싼 프로브부터 (순서 고정)

### ① 선언된 값 말고 **실제 주입된 값**을 본다
설정 파일을 하나씩 열어보는 건 대개 시간 낭비다. 프로세스에 실제로 들어간 값을 먼저 본다.
> 실제 사례: 인증 오류를 쫓느라 설정 파일 네 개를 전부 열어봤는데 다 정상이었다. 실제 원인은 프로세스가 물고 있던 **캐시된 옛 토큰**이었고, `ps -E -p <PID>` 한 줄이면 갈렸다.

프로세스가 **최신 코드인지**도 여기서 본다 (기동 시각 vs 최신 변경 시각, 빌드 산출물에 그 파일이 있는지).

### ② 대조군을 만든다 — 명백히 틀린 값을 넣어본다
결과가 같으면 그 관측으로는 아무것도 증명 못 한다.
> 실제 사례: 올바른 enum 값으로 조회해도 0건, 존재하지 않는 값으로 조회해도 0건이었다. 「정말 없음」과 「서버가 못 알아들음」이 겉으로 똑같았다.

### ③ 그래도 안 갈리면 **명세를 연다**
실행을 반복하지 말고, **허용값이 선언된 곳**에서 확인한다. 어디에 있는지는 스택마다 다르니 **먼저 이 프로젝트의 명세 위치부터 찾는다.**

| 어디 | 무엇을 본다 | 예시 (프로젝트마다 다름) |
|---|---|---|
| **API 스펙** | 허용 enum, 필수 파라미터, 응답 형태 | Spring+springdoc이면 `/v3/api-docs`·Swagger UI / 다른 스택이면 `openapi.yaml`·`api-spec.json` |
| **FE 생성 타입** | 실제로 배선된 요청·응답 타입 | Orval 생성물, `packages/repositories` 같은 Request 타입 |
| **BE 소스** | enum 클래스, 상수, validation 애너테이션 | 스펙이 `type: string` 이라 판정 불가일 때 최후 |
| **DB** | 제약조건, CHECK, FK | 값의 진짜 경계 |

⚠️ **스펙이 `type: string` 이면 어떤 값이 와도 "스펙 위반 아님"** 이다 — 그건 판정 근거가 없다는 뜻이지 정상이라는 뜻이 아니다. 그때는 BE 소스나 DB로 한 칸 더 내려간다.

### ④ 묻기 전에 직접 호출한다
"이 API 되나요?"를 남에게 묻기 전에 개발 서버에 직접 쳐본다. 답을 기다리는 동안 작업이 멈춘다.
> 실제 사례: 직접 호출해보니 이미 지원되고 있어서 물어볼 필요가 없었다. 단, **파라미터명을 지어내지 말 것** — 지어낸 이름으로 호출해놓고 "필터가 동작하지 않는다"고 오판한 적이 있다.

⚠️ **읽기(GET)와 쓰기(POST/PUT/DELETE)를 다르게 취급한다.**
- 읽기는 자유롭게 친다.
- **쓰기는 대상 DB를 먼저 확인한다.** 로컬 서버가 로컬 DB를 보는 게 아니라 **공유 dev DB에 붙어 있는 경우**가 있다 — 그러면 내가 만든 테스트 데이터가 남의 화면에 남는다.
  > 실제 사례: 로컬에서 띄운 서버가 로컬 DB가 아니라 **공유 개발 DB**를 보고 있었다. 화면에서 만든 테스트 데이터가 남의 화면에 그대로 남았다.
- 쓰기가 꼭 필요하면 **임시 계정/임시 값으로 하고 끝나면 되돌린다.**

## Step 5 — 관측 신뢰도 검사 (로컬에서 본 값으로 단정하기 전)

로컬/개발 환경 값으로 "버그다 / 데이터가 오염됐다"고 말하기 전에 순서대로 가른다.
> 실제 사례: **같은 화면에서 두 번 재발**했다. 진행 단계 표시가 전부 같은 색이라 "색 로직 버그"로 두 번 단정했는데, 실제로는 그 환경의 데이터가 전부 최종 단계여서 정상 동작이었다.

1. **프로세스가 최신인가** — 기동 시각 vs 최신 변경
2. **목(mock)인가 실제 응답인가** — MSW 등 목 레이어 유무
3. **시드인가 실데이터인가 — 이분법 말고 비율로** — 생성일 분포로 확인. 둘이 **섞여** 있을 수 있다
4. **화면에서 본 값이 전체의 몇 %인가** — 첫 페이지에 걸린 소수를 전체로 오인하기 쉽다. `GROUP BY` 한 줄
5. **판정할 계약이 있는가** — 스펙이 `type: string` 이면 어떤 값이 와도 **스펙만으론 판정 불가**

## Step 6 — 원인 확정

- **증상 ≠ 원인.** 에러 클래스 이름은 증상이다.
  > 실제 사례: `NoClassDefFoundError` 는 증상이었다. 원인은 테스트용 컨테이너를 정리하는 프로세스가 테스트 도중에 끼어든 것이었고, 해법은 환경변수 한 줄이었다. 에러 클래스 이름만 검색했다면 영영 못 찾았다.
- **멈추는 기준**: "이걸 알았으면 안 틀렸다" 는 지점. 보통 "왜?" 2~3번.
- **인과가 애매하면 되돌려서 확정한다** — 의심 커밋만 `git checkout` 해보고 증상이 사라지는지 본다. 머리로 못 찾으면 헤매지 말 것.
- 확정하면 **어느 층인지 / 무엇을 고치면 되는지**를 한 줄로 쓴다.

## Step 7 — 넘기기

- 층이 **표시**로 갈렸거나 증상을 눈으로 재현해야 하면 → **`loop:browser`**
- 고칠 준비가 됐으면 → 수정 후 **`loop:review`** (특히 렌즈 2·3)
- 놀랄 만한 원인이었으면 → **`loop:retro`** 로 교훈을 굳힌다

## 금지

- ❌ 증상 문장 없이 코드부터 열기
- ❌ 층을 안 가르고 파일을 훑기
- ❌ grep 히트 줄만 보고 원인 단정 (블록을 통째로 읽는다)
- ❌ 같은 실행을 반복하며 다른 결과 기대하기 — 안 갈리면 명세로
- ❌ 로컬에서 본 값을 Step 5 없이 "버그"로 단정
- ❌ 에러 메시지 이름을 원인으로 적기
- ❌ 인과 확정 전에 고치기 시작
- ❌ 직접 확인 가능한 걸 남에게 먼저 묻기
